Принцип согласования (решение пользователя): терминал подстраивается под архитектуру платформы, а не наоборот — проще доработать один сервис, чем переписывать три работающих, спроектированных под объединение с CRM.

## ❌ Демо-счёт: почему отклоняем и что вместо

**Их вариант** («кабинет читает наш `/account`») создаёт вторую, синхронную модель интеграции ровно там, где вся платформа событийная:
1. Нарушает золотое правило (§3 брифа CRM, ADR-018): никаких синхронных вызовов соседей на пути клиента. Лёг терминал — лёг дашборд кабинета.
2. CRM-интеграция уже спроектирована на потреблении событий; счёт клиента — то, что CRM обязательно захочет видеть. События дают CRM ту же модель подключения, что и лиды, — без доработок терминала.
3. У нас готова вся инфраструктура: конверт v1, шина `platform.events`, дедуп по event_id, релей как референс producer-паттерна.

**Наш вариант**: терминал владеет торговым состоянием (позиции, маржа, P&L — его домен, исполнение требует локальной истины) и **публикует события** в конверте v1: `terminal.account.opened`, `terminal.trade.executed`, `terminal.balance.changed` (финальный набор — в спеке). Кабинет ведёт `demo_accounts` как **проекцию** (консюмер событий), CRM подключается к тем же событиям без единой доработки терминала. Стартовый баланс тенанта — из конфига сайта в CMS. Terminal-side реализация — transactional outbox (образец — наш `apps/relay`, отдадим схему и код как референс).

## Наши встречные обязательства (мы блокируем их работы — отдаём первыми)

1. **Theming-пакет** (для их адаптера, M): `tokens.css` как версионируемый артефакт + `cms.brand.schema.json` + живой пример `GET /v1/cms/brand` — всё уже существует, собрать пакет — день.
2. **JWT/JWKS-спека** (для их SSO): claims (`sub` = наш userId, `tenant`, `exp` ≤ 60 c, one-shot `jti`), алгоритм RS256 или EdDSA, JWKS-эндпоинт. Появляется вместе с нашим **Auth-сервисом** — триггер ADR-017 сработал (один терминал × много сайтов).
3. **Мульти-тенантный контракт CMS**: коллекция sites, `/v1/cms/*?site=` (бренд, инструменты-allow-list, стартовый демо-баланс, локали сайта) — наш следующий крупный этап CMS; их L-работа по тенантам зависит от этого контракта.
4. **Схемы событий терминала** в platform-contracts — пишем вместе с ними (наш конверт, их payload'ы).
5. **Символ-маппинг**: таблица наших канонических символов ↔ их инструментов (поле в CMS instruments, напр. `terminalSymbol`).

## Совместная дорожная карта

- **Фаза Т1 — бренд** (не ждёт ничего): мы → theming-пакет; они → сведение токенов + рантайм-загрузчик (M), конфигурируемый frame-ancestors (S). Результат: их страница красится из нашей админки (пока один тенант).
- **Фаза Т2 — SSO + тенанты**: мы → Auth-сервис + JWT-спека, CMS sites + `?site=`; они → проверка JWT + сессия + тенант per-request (M–L + L). Результат: пользователь кабинета попадает в СВОЙ терминал СВОЕГО сайта.
- **Фаза Т3 — события + инструменты**: они → outbox + события в шину, allow-list per-tenant (M+); мы → консюмер (проекция demo_accounts, уведомления кабинета). Параллельно i18n (M–L).

## Дополнение 2026-07-25: Market Data Service (ADR-024)

Решение пользователя: котировки всей экосистемы идут через **единый сервис MDS** (все API-ключи провайдеров только там; управление инструментами/провайдерами — из CMS). Для терминала это значит: **upstream меняется с прямого Binance на MDS**, символ-маппинг у терминала снимается (MDS отдаёт канонические символы платформы), подписка по символам решается на нашем fan-out. Данные для их «фазы данных» подключаем позже — сначала White Label-цепочка (темизация → SSO → события).

## Финализация (ответ на их ответ, 2026-07-25) — контракт замкнут

Их встречный документ: архитектура принята полностью, `/account`-предложение отозвано ими же (outbox ложится в их транзакцию `with_account` — producer без переписывания торговли). Три их вопроса — закрыты решениями:

**A. Ключ тенанта (формат и главный источник).** `site` — slug из реестра CMS (`^[a-z0-9-]{2,32}$`, напр. `apex-ru`), реестр — коллекция sites (этап Т2). **Основной источник — `?site=`, обязателен ВСЕГДА** (и до, и после логина); поддомен — опциональная косметика прода. В авторизованном режиме `token.tenant` обязан совпадать с `?site=`; несовпадение — 403 (их проверку подмены одобряем, это правильная паранойя).

**B. Единый логаут.** Выбираем **вариант 1 + бесплатное усиление**: сессия терминала с TTL ≤ 15 мин + тихий ре-handoff (iframe шлёт родителю `postMessage {type:'token.refresh.request'}` → родитель отвечает свежим JWT, если сессия платформы жива; погашена → отказ → терминал разлогинивается). Плюс **best-effort мгновенный сигнал**: страница кабинета при выходе шлёт `postMessage {type:'logout'}` в iframe (она в этот момент жива — ноль новой инфраструктуры). Итог: мгновенный UX-логаут + жёсткая гарантия ≤ TTL. Вариант с шиной отклонён: логаут — realtime-операция, at-least-once с задержками ей не подходит, и шина ещё без кредлов.

**C. Живой P&L — принято.** Проекция `demo_accounts` кабинета = реализованный баланс + открытые позиции; плавающий P&L/equity кабинет в MVP НЕ считает и НЕ обещает (полная картина — внутри iframe терминала). После появления MDS (ADR-024) кабинет сможет считать equity из тех же цен — отдельным решением.

**Символ-маппинг — упрощаем по их подсказке**: маппим на их **числовой instrument id** (стабильнее строк); в CMS instruments появится поле `terminalInstrumentId` (этап sites). Их `BTC-USDT` ≈ наш формат — расхождений меньше, чем ожидали.

**R-T3 (подписка по символам)**: их предложение сделать `/v1/stream?symbols=` в конце Т1 — поддерживаем в их приоритете, но для нас это перестало быть блокером: сайты пойдут за котировками в MDS (ADR-024), который берёт данные у провайдера напрямую, а не через терминал.

**Четыре добора, которые они запросили, — статус:**
1. ✅ **Theming-пакет отдан**: `packages/api-client/artifacts/theming-pack/` (tokens.v1.css + cms.brand.schema.json + живой brand.example.json + README-спека загрузчика). Т1 разблокирован.
2. ✅ **Референс producer**: репо публичное — `apps/relay/` (poll FOR UPDATE SKIP LOCKED, backoff, confirm-channel) + схема outbox `db/init/001_init.sql`; конверт v1 — `packages/api-client/artifacts/json-schema/events.envelope.v1.schema.json` (+ lead.submitted как образец payload-схемы).
3. 🔒 **Тех шины**: RabbitMQ, topic-exchange `platform.events`, publisher confirms, persistent, `messageId=event_id`, дедуп на консюмерах по `event_id` (ADR-019). Параметры подключения (host/vhost/креды) — после созвона §10 с CRM (мы сами ждём их же для релея).
4. ✅ **Решения A и B** — выше.

## Ответы платформы на вопросы Т2 (2026-07-25, вечер)

Их Т1 принята (терминал красится из CMS; коллизию `--accent`→`--brand` одобряем — наши токены каналами, их семантика поверх). Связка живая: `NEXT_PUBLIC_TERMINAL_URL=http://localhost:8888` подключён, `/trade` кабинета рендерит терминал с `?site=apex-ru&locale=ru`, родитель уже шлёт `sso.token` при загрузке (игнорировать его до Т2 — нормально).

1. **Bearer-в-памяти вместо cookie — ✅ да, делайте так.** Third-party-куки в iframe мертвы (Safari давно, Chrome добивает) — держите сессию bearer-токеном в памяти страницы. Перезагрузка iframe теряет токен? Не страшно: шлёте `token.refresh.request`, родитель переотдаёт за миллисекунды. Модель не меняется.
2. **Origins.** Терминал встраивает и шлёт postMessage ТОЛЬКО кабинет (сайты — витрины, они не встраивают): dev — `http://localhost:3002`. Это и `frame-ancestors`, и проверка `event.origin`. Прод-origin'ы (`https://my.<домен>`) — при VPS-деплое, пришлём списком.
3. **Живой JWKS (dev)**: `http://localhost:3002/api/sso/jwks` — уже отдаёт. **Свежий токен**: эндпоинт same-origin-only (по сессионной куке) — зарегистрируйтесь на `http://localhost:3002/register`, затем в консоли браузера: `await (await fetch('/api/sso/token', { method: 'POST' })).json()`. Токен живёт 60 с — для тестов валидатора генерируйте по требованию.
4. **Ключ счёта — подтверждаем: `(tenant, sub)`.** Оба берите из провалидированного токена, не из query.
5. **Мульти-инстанс терминала: сейчас и в обозримом — ОДИН** (ADR-023: один мульти-тенантный инстанс). Replay-защита по `jti` в памяти процесса — достаточна. Если соберёмся масштабировать горизонтально — предупредим заранее (понадобится общий стор jti).
6. **Де-риск (предсобрать JWT-валидатор против примеров) — поддерживаем**, примеры в sso-pack для этого и лежат.
7. **⚠️ CMS-ключ — не для браузера.** `X-API-Key` в клиентском JS станет публичным. Запрашивайте brand через ваш gateway (у вас уже есть прокси-слой): браузер → ваш gateway → CMS с ключом server-side. Живой dev-эндпоинт: `GET http://localhost:3001/v1/cms/brand?site=apex-ru` (ключ передан отдельно).
8. **Mixed content**: локально обе стороны http — ок; на staging/prod TLS с обеих сторон (решается VPS-этапом, terminal получит `https://trade.<домен>`).

## Ответ на их Т2-финал (2026-07-25, поздний вечер)

Их Т2 принята (валидатор по чеклисту, bearer в памяти, счёт `(tenant, sub)` персистентно, dev-тумблер SSO_DISABLED — всё ровно по контракту).

**Вопрос по brand — решён вариантом (б), публичный `?site=` уже живой**: `GET /v1/cms/brand?site=<slug>` теперь отдаётся БЕЗ `X-API-Key` и с CORS `Access-Control-Allow-Origin: *` (браузерный fetch с их origin работает напрямую, «редирект на /login» им не грозит — они, судя по симптому, стучались в кабинет :3002 вместо CMS :3001; правильный dev-URL: `http://localhost:3001/v1/cms/brand?site=apex-ru`). Обоснование публичности: бренд публичен по определению (виден на сайте), и дологинная страница терминала обязана краситься, когда postMessage-токена ещё нет — вариант (а) это не решает. Границы сохранены: brand без `?site=` и все остальные ресурсы — по-прежнему только с ключом; draft-режим публичным не бывает.

**Полный e2e handoff** — с нашей стороны всё готово и живое: кабинет встраивает iframe `?site=apex-ru&locale=ru`, шлёт `sso.token` на onload, отвечает на `token.refresh.request`, JWKS на `:3002` живой. Осталось: они включают `SSO_DISABLED=0` — и прогоняем совместно (регистрация на `:3002` → /trade → сделка от лица юзера → событие увидим в их логах).

## Стартовый баланс тенанта (2026-07-25, после первого живого прогона)

Замечено на живой связке: обзор кабинета показывает $10 000 (наша проекция), терминал — $100 000 (их дефолт). Два разных вопроса:

1. **Стартовый баланс** — по финализации берётся из конфига сайта в CMS. Ручка готова: **`GET /v1/cms/sites/{slug}`** (под `X-API-Key`, server-side их гейтвея — НЕ публичная) → `{ slug, name, demoStartBalanceCents }` (+ `X-Content-Version`). Просьба к терминалу: при заведении счёта тенанта читать `demoStartBalanceCents` отсюда (кеш + инвалидация по возможности; частота изменения — «почти никогда»). Для `apex-ru` сейчас 1 000 000 центов = $10 000.
2. **Живая синхронизация после сделок** — это Т3 (события `terminal.balance.changed` → проекция кабинета), ждёт кредлов шины. До Т3 «Обзор» кабинета сознательно показывает только стартовую проекцию — это зафиксированное решение C (без плавающего P&L), не баг.

## Риски (журнал)

- **R-T1**: данные терминала — только крипта (топ-30 Binance); маркетинг сайтов обещает 6 категорий/12 000+ инструментов. Первая фаза = крипто-демо. ✦ Закрывается ADR-024: новые категории = новый провайдер в MDS, терминал/сайты не трогаются.
