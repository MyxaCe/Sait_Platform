# Что требуется от других команд — для полноценной демо-торговли

Контекст: прямой путь демо-торговли (логин → /trade → терминал с брендом, SSO и котировками) на нашей стороне **готов и проверен e2e**. Чтобы демо-торговля стала полноценной (сделки отражаются в кабинете, единый стартовый баланс, единый список инструментов), нужны действия смежных команд. Ниже — только то, что зависит НЕ от нас. Наша часть — в [[Задачи]].

Статусы: 🔴 блокирует · 🟡 желательно · 🔒 ждёт кредлов шины

---

## От команды ТЕРМИНАЛА

1. 🔴 **Server-side чтение конфига тенанта.** Ручка `GET /v1/cms/sites/{slug}` (стартовый демо-баланс `demoStartBalanceCents` + allow-list инструментов сайта) отдаётся **под `X-API-Key`, только сервер-сервер**. Из браузера — 401. Терминал должен читать её своим гейтвеем (ровно как уже делает для `brand`). Ключ — не в клиентский JS.
2. 🔴 **Стартовый баланс демо-счёта — из `demoStartBalanceCents`.** Сейчас у терминала свой дефолт ($100k), у нас $10k → расхождение в «Обзоре». Брать значение из CMS при заведении счёта тенанта (для `apex-ru` = 1 000 000 центов).
3. 🔴 **Уважать allow-list per-site.** Показывать только инструменты из `sites/{slug}.instruments`, остальное скрывать. Это регуляторика (разные страны — разные разрешённые инструменты), не косметика.
4. 🟡 **Символ-маппинг — подтвердить или снять.** Нужно ли поле `terminalInstrumentId` (обещано в финализации ADR-023), или ваши инструменты уже совпадают с нашими каноническими символами MDS (`BTCUSDT`↔`BTCUSD`)? Если совпадают — поле не заводим. Если нет — пришлите соответствие «канонический символ ↔ ваш id», заведём поле в CMS.
5. 🟡 **Переключить upstream котировок на MDS.** Вместо прямого Binance — наш MDS: публичный REST `GET /v1/instruments`, `GET /v1/quotes?symbols=`; WS (socket.io) `subscribe`/`unsubscribe` → `quotes:batch`. CORS `*`, подписка по символу уже готова, символы канонические (маппинг у вас снимается). Dev: `http://localhost:3003`.
6. 🔒 **Обратный контур (Т3): публикация событий счёта.** Outbox в вашу транзакцию открытия/изменения счёта + публикация в `platform.events` (конверт v1, `message_id=event_id`, дедуп по `event_id`): `terminal.account.opened`, `terminal.trade.executed`, `terminal.balance.changed` (payload'ы согласуем совместно). Референс producer-паттерна — наш `apps/relay` + схема outbox `db/init/001_init.sql` (репо публичное). Ждёт кредлов шины (см. CRM).
7. 🟡 **Прод-инстанс терминала + frame-ancestors.** Достижимый URL (`https://trade.<домен>`), на который направим `NEXT_PUBLIC_TERMINAL_URL` (сейчас dev `:8888`). `frame-ancestors` — список наших origin'ов кабинета (`https://my.<домен>`), пришлём при VPS-деплое. TLS с обеих сторон (mixed content).
8. 🟡 **Подтвердить имена postMessage.** Актуальный контракт (sso-pack): `sso.token` / `token.refresh.request` / `sso.logout`. В старых заметках мелькал `logout` — фиксируем `sso.logout`.
9. 🟡 **i18n ru/en** — минимум к первому сайту (`?locale=` уже передаём).
10. 🟡 **GlitchTip** — присоединиться (свой проект, наша scrubbing-политика).

## От команды CRM

1. ✅ **Кредлы шины `platform.events` — получены (тестовый VPS, 2026-07-27).** Продюсер (site-web → lead.submitted) подтверждён обеими сторонами; наш обратный контур (консюмер) прогнан вживую против этой шины. Осталось: TLS (amqps) + фаервол для боевого; пункт 1a ниже.
1a. 🔴 **Отдельный бус-пользователь для КОНСЮМЕРА кабинета.** Кредл `site-web` — **publish-only**: консюмер получил `403 ACCESS_REFUSED` на `queue.declare` (у site-web есть configure на exchange, но не на очереди). Нужен пользователь (напр. `cabinet`) с правами: `configure`+`write`+`read` на очередь `cabinet.terminal-projection` (и её DLX), `read` на exchange `platform.events`. Либо CRM заранее объявляет очередь+binding и даёт нам `read`. (Для теста мы временно подключили консюмер под management-admin — это НЕ для боевого.)
2. 🟡 **Хостинг общего контракт-репозитория `platform-contracts` (git).** Куда положим конверт v1 и схемы событий (у нас конверт готов, отдадим). Предлагали завести git-репо.
3. 🟡 **GlitchTip-инстанс на вашем VPS.** Для наших SDK (site-web, cabinet, consumer). Бэкапы/обновления — на вашей стороне (ADR-014).
4. 🟡 **Факт запуска PII scrubbing-политики** (блокер первого события GlitchTip; политика согласована ADR-014).

## Совместное (мы + терминал, в platform-contracts)

- **Схемы событий `terminal.*` в конверте v1**: наш конверт — их payload'ы. Первый черновик схем сделаем мы (конверт готов) и отдадим на согласование — это разблокирует и нас (консюмер), и вас (продюсер).
