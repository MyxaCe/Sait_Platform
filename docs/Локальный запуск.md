# Локальный запуск

Как поднять монорепозиторий на своей машине и что происходит без каждой
переменной окружения. Проверено 2026-09-03 на Windows 11 (задача WEB-01).

Раздел про сайт (`apps/web`) проверен целиком. Кабинет, релей и консюмер
дописываются задачами CAB-01, REL-01, CON-01.

## Версии

| Что | Версия | Откуда требование |
| --- | --- | --- |
| Node | 20+ (проверено на 24.18.0) | `package.json` → `engines.node` |
| pnpm | 9.15.0 | `package.json` → `packageManager` |
| Next.js | 14.2.35 | `apps/web/package.json` |

Пакетный менеджер только pnpm: репозиторий — pnpm-workspace
(`pnpm-workspace.yaml`: `apps/*`, `packages/*`), `npm install` разложит
зависимости иначе и сломает `workspace:*`-ссылки на общие пакеты.

## Сайт без соседей — минимальный запуск

**Соседи не нужны вообще.** Ни CMS, ни MDS, ни Postgres, ни шина. Файл `.env`
создавать не обязательно: все переменные имеют дефолты или ветку «не задано».

```bash
pnpm install          # ~40 с, 734 пакета
pnpm --filter @broker/web dev
```

Сайт: <http://localhost:3200>. Русский — без префикса (`/instruments`),
английский — с префиксом (`/en/instruments`); автодетект по `Accept-Language`
отключён сознательно (`i18n/routing.ts`, баг B-005).

### Почему 3200, а не 3000

Порт задан явно (`next dev -p 3200`), и это не косметика. Без `-p` Next при
занятом порте **молча** уходит на соседний, напечатав одну строку
`⚠ Port 3000 is in use, trying 3001 instead`. Строку легко пролистать, а дальше
открывший 3000 видит чужое приложение вместо своего.

Что занято на этой машине и почему туда нельзя:

| Порт | Кто | Почему не мы |
| --- | --- | --- |
| 3000 | `mica-v2-frontend-1` — фронтенд CRM Mica | чужая система, вне зоны работ |
| 3001 | закреплён за CMS решением штаба | локальные умолчания не расходятся с контуром |
| 3002 | кабинет (`next dev -p 3002`) | своё, занято |
| 3100 / 3101 / 3102 | контур `broker-local-*`: web / cms / cabinet в Docker | поднимает команда deploy |
| **3200** | **dev-сервер витрины** | свободен, проверено |

Production-сборка, если нужна именно она (`next start` порт не пинит — задавать
через `PORT`):

```bash
pnpm --filter @broker/web build
PORT=3200 pnpm --filter @broker/web start
```

## Проверка, что связи действительно мягкие

Ровно то, чем закрыта WEB-01 — воспроизводится за минуту:

```bash
# 1. Юнит-тесты изоляции (8 тестов на getCms + 4 на cmsFetch)
pnpm --filter @broker/web test
pnpm --filter @broker/api-client test

# 2. Живой обход: все 67 URL карты сайта при погашенных CMS и MDS
curl -s http://localhost:3200/sitemap.xml \
  | grep -o '<loc>[^<]*</loc>' | sed 's|<[^>]*>||g; s|https://example-broker.com|http://localhost:3200|' \
  | while read -r u; do
      code=$(curl -s -o /dev/null -w '%{http_code}' "$u")
      [ "$code" = 200 ] || echo "NOT200 $code $u"
    done
```

Результат прогона 2026-09-03: 67/67 → 200, в логе сервера ни одного
необработанного исключения (единственные предупреждения — webpack-кеш
`next-intl`, чужая библиотека, к нашему коду отношения не имеет).

**Граница этой проверки.** Проверялось поведение при **отсутствующей** CMS, то
есть против фикстур и собственного кода изоляции. Ни одна реализация CMS сюда
не входила — ни legacy, ни v2. Утверждать по этому прогону что-либо о контракте
с CMS нельзя; это отдельная работа против живого контура (`:3101`), и она,
по решению Р-014, будет проверкой **против legacy-CMS**, а не против того, что
поедет в прод.

## Сначала докажи, что отвечает твой процесс

На этой машине **одновременно работают два экземпляра этого же приложения**:
твой локальный и контурный `broker-local-web-1` в Docker на 3100. Приложение
одно, конфигурация разная — и по ответу их не различить:

```
/api/health на 3100 → {"status":"ok","service":"site-web","time":…}
/api/health на 3200 → {"status":"ok","service":"site-web","time":…}
```

`service: "site-web"` называет ПРИЛОЖЕНИЕ, а не экземпляр — это и подвело.

**Теперь ручка отвечает на вопрос «кто ты».** По решению штаба (B-019) в
`/api/health` добавлены два поля:

```json
"instance": { "host": "Billi", "pid": 7976, "startedAt": "…" },
"config":   { "DATABASE_URL": false, "CMS_API_URL": false, … }
```

- `instance` называет **экземпляр**, и признаки подобраны так, что экземпляр не
  выбирает их себе сам: `host` в контейнере — его id, на хосте — имя машины;
  `pid` разводит два процесса на одной машине. Самоназвание не годится по
  построению — именно оно было одинаковым у обоих.
- `config` — **отпечаток**: какие переменные заданы, но не что в них лежит.
  Только булевы значения; ручка не должна становиться местом утечки.

`FRAME_ANCESTORS` в отпечаток сознательно не входит: он читается на сборке, и в
готовом образе `process.env` его уже не содержит — поле сказало бы «не задано»
о действующем значении. Про `NEXT_PUBLIC_*` читать точно: отпечаток отражает
взгляд **сервера**; клиентский бандл несёт значение, вшитое на сборке.

Порядок, прежде чем считать любой ответ свидетельством:

1. смотреть в вывод СВОЕГО процесса — `✓ Ready` и строку `Local: …` с портом;
2. `EADDRINUSE` означает, что твой сервер не поднялся, а порт отвечает чужой.
   Именно так проверка «что будет без переменной» едва не была подтверждена на
   экземпляре, где переменные **заданы** (баг B-019);
3. сверить `instance.host` и `instance.pid` с тем, что напечатал свой процесс.
   Это заменяет прежний способ «угадать по `database: skipped`»: тот отличал
   конфигурацию, а не личность.

## Переменные окружения сайта

Шаблон — `apps/web/.env.example`. Ни одна переменная не обязательна для
запуска; таблица говорит, чем платишь за каждую незаданную.

Таблица проверена не чтением кода, а наблюдением: `.env`, `.env.local` и
`.env.development` в репозитории отсутствуют (есть только `.env.example`,
который Next не читает), переменные не заданы и в оболочке, а эффект каждой
снят с работающего процесса на 3200.

| Переменная | Где читается | Не задана → |
| --- | --- | --- |

## Два разных пути отказа CMS

Их постоянно смешивают, а ведут они через разный код и требуют разной проверки.

**«CMS не настроена»** — `CMS_API_URL` пуст. Сайт **знает заранее**, что боевых
данных не будет: `getCms` не идёт в сеть вообще, строит контент локальным
билдером и кладёт в `unstable_cache` с теми же тегами `cms:{resource}`, что и
боевой путь — вебхук-инвалидация ведёт себя одинаково в обоих режимах. Это
штатная конфигурация контура, и в логе ошибок ей делать нечего.

**«CMS отвалилась в рантайме»** — `CMS_API_URL` задан, сайт уходит за данными и
**узнаёт об отказе по факту**: отклонённое соединение, 5xx, таймаут 3 с, мусор
мимо Zod-схемы. Работает страховка `cmsFetch` (`packages/api-client/src/server.ts`):
timeout → валидация → фолбэк на фикстуры, и каждый фолбэк обязан прокричать в
лог — фолбэк без алерта это скрытая авария (риск R-15).

Чем какой путь покрыт:

| Файл | Что проверяет | Какой путь |
| --- | --- | --- |
| `apps/web/lib/cms-mock.test.ts` | билдеры фикстур в обеих локалях проходят Zod-контракт | **ни один**: это контрактный тест данных, `getCms` не вызывается |
| `packages/api-client/src/server.test.ts` | `cmsFetch` при отказе/5xx/мусоре отдаёт фолбэк | рантайм — но на синтетической схеме, без проводки сайта |
| `apps/web/lib/cms.test.ts` | `getCms` на обоих ветках + поломка самой фикстуры | оба, на настоящих фикстурах сайта |

## Граница доступа к инструментам отказывает по-своему (ADR-029)

Два пути выше — про **контент**, и оба заканчиваются фикстурами. У allow-list'а
с карточки сайта путей четыре, и все четыре заканчиваются **запретом**, потому
что это граница доступа, а не каталог:

| Что произошло | Состояние | Видно на экране |
| --- | --- | --- |
| список получен и непуст | `allowed` | обычный список, объяснений нет |
| список получен и пуст | `empty` | «Инструменты пока не выбраны», `data-access-state="empty"`, причины нет — ничего не ломалось |
| `CMS_API_URL` не задан | `unavailable: not-configured` | «Список разрешённых инструментов недоступен», причина в разметке и на экране |
| CMS ответила не-2xx | `unavailable: http-error` | то же, причина другая |
| соединение, таймаут, мусор | `unavailable: network` | то же |
| ответ без `instruments[]` | `unavailable: malformed` | то же. **Не** пустой список: источник ничего не сказал |

Проверяется подъёмом поддельной CMS, которая отдаёт нужный ответ на
`/cms/sites/{slug}` и `404` на остальное, — тогда контент идёт из фикстур, а
граница меняется независимо от него. Кеш `fetch` живёт в `.next/cache/fetch-cache`
и **переживает рестарт dev-сервера**: без его очистки следующий режим отвечает
данными предыдущего.

## Отличим ли фолбэк от настоящих данных

Проверено отдельно: отказ не должен выглядеть правдоподобным значением.

**CMS → фикстуры: отличимо для разработчика, неотличимо для посетителя.** Каждый
сработавший фолбэк пишет `[cmsFetch] falling back to fixtures path=… locale=…` и
при заданном `SENTRY_DSN` уезжает в GlitchTip. В самой странице признака нет —
для маркетингового сайта это осознанно: показать посетителю прошлогодний, но
валидный текст лучше, чем пустоту. Единственный видимый след — даты в новостях
и вебинарах (`features/analytics/news-data.ts`: июль 2026), они стареют вместе
с фикстурами.

**MDS → мок-фид: отличимо, но только после исправления B-018.** Раньше было
неотличимо ни для кого: мок рапортовал `connected`, индикатор горел зелёным с
подписью «Данные в реальном времени» над случайным блужданием. Теперь без
`NEXT_PUBLIC_WS_URL` фид переходит в состояние `simulated`, и над лентой
котировок появляется полоса «Демо-данные: цены не рыночные» — видимым текстом,
а не только цветом точки и тултипом.

Решает это `RealtimeService` по наличию адреса источника, а не сам драйвер:
подделать подлинность нельзя даже тестовым фейком. Признак подлинности,
который сообщает о себе проверяемый компонент, не является признаком.

Практическое следствие для локального запуска остаётся: **цены на локальном
сайте выдуманы всегда.** Скриншот локального сайта с котировками нельзя
использовать как свидетельство работы фида — теперь на самом скриншоте это
хотя бы написано.

## Ключ подписи SSO — без него JWKS отдаёт 503

`GET /api/sso/jwks` кабинета отвечал `503 {"error":"sso_not_configured"}`. Это
не поломка ручки: не задана `SSO_PRIVATE_KEY_B64`, и кабинету нечем подписывать
handoff-токены. Ручка при этом ведёт себя правильно — **отказ назван причиной**,
а не пустым JWKS: пустой список ключей терминал прочитал бы как «ключей нет,
подпись не проверить», то есть отказ выглядел бы данными.

Пока ручка отдаёт 503, сквозная проверка платформы невозможна: терминал
валидирует токен по JWKS, и валидировать ему нечем.

### Что именно требуется

| | |
| --- | --- |
| Переменная | `SSO_PRIVATE_KEY_B64` (приложение `cabinet`) |
| Что в ней | приватный ключ RSA, **PKCS#8 PEM, закодированный в base64** |
| Длина ключа | не меньше 2048 бит |
| Кодирование | одна строка **без переносов** — PEM с переносами в `.env` не живёт |
| Алгоритм | RS256, `kid` = `platform-sso-1` (`apps/cabinet/lib/sso/jwt.ts`) |
| Публичная половина | **не хранится**: JWKS выводится из приватного ключа на лету (`createPublicKey`), хранить пару не нужно |

Читает переменную только кабинет — ни сайт, ни релей, ни консюмер её не видят.

### Генерация ключа для разработки

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048   | openssl pkcs8 -topk8 -nocrypt -outform PEM   | base64 -w0
```

Без openssl (Windows, node уже стоит):

```bash
node -e "const{generateKeyPairSync}=require('node:crypto');console.log(Buffer.from(generateKeyPairSync('rsa',{modulusLength:2048}).privateKey.export({type:'pkcs8',format:'pem'})).toString('base64'))"
```

**`-w0` обязателен.** Без него GNU base64 переносит вывод по 76 символов, в
`.env` попадает только первая строка — переменная «задана», отпечаток
конфигурации показывает `true`, а `importPKCS8` падает. Отказ при этом
выглядит как поломка кода, а не как обрезанный ключ. На macOS флага `-w` нет:
`| base64 | tr -d '
'`.

### Куда класть значение

В `apps/cabinet/.env.local` — он покрыт `.gitignore` (проверено не чтением
правила, а `git check-ignore -v apps/cabinet/.env.local` → `.gitignore:8`;
правило, которое выглядит рабочим и не срабатывает, у нас уже было).

**В репозиторий значение не кладём ни в каком виде.** Репозиторий публичный,
пуш — это публикация. В `apps/cabinet/.env.example` лежат только имя
переменной и способ получения; на контуре и в проде значение выдаёт команда
`deploy` и держит в `deploy/vps/.env` рядом с compose (chmod 600).

Dev-ключ и ключ контура **обязаны различаться**: тот, у кого есть ключ, может
выписать себе токен входа в терминал от имени любого пользователя.

### Чем проверено

Кабинет поднят на запиненном порту `3202` (не 3002 — чтобы не спутать с
контурным экземпляром, урок B-019), `.env.local` с ключом:

```
/api/health  → instance {host: "Billi", pid: 54064}, config.SSO_PRIVATE_KEY_B64: true
/api/sso/jwks → HTTP 200, keys[0] = {kty: RSA, kid: platform-sso-1, alg: RS256, use: sig}
/api/sso/token (без сессии) → HTTP 401 unauthorized
```

`pid` в ответе сверен с процессом, слушающим 3202: отвечал **тот экземпляр,
которому дали ключ**, а не соседний.

Отдельно прогнан путь терминала целиком: токен подписан ключом кабинета и
проверен через `createRemoteJWKSet` **по сети с живой ручки** — подпись
принята, `alg = RS256`, `kid = platform-sso-1`, `tenant = apex-ru`,
`exp − iat = 60` секунд. Контрольный прогон: токен, подписанный чужим ключом с
тем же `kid`, отвергнут (`ERR_JWS_SIGNATURE_VERIFICATION_FAILED`) — то есть
ручка отдаёт именно нашу публичную половину, а не что-нибудь, что проходит
всегда.
