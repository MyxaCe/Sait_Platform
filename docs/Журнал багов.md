# Журнал багов

Каждый баг: симптом → причина → решение → урок. Новые записи добавляются сверху раздела «Исправленные».

## Исправленные

### B-024 · Подпись индикатора обещала данные, а поднималась по открытому сокету

- **Симптом**: точка состояния горела с подписью «Данные в реальном времени» / «Real-time data», а поднималась она по событию открытия сокета браузер→MDS. Молчащий, но открытый сокет — `disconnect` не приходит, данные не идут — выглядел живым фидом. Найдено штабом, закрыто задачей CAB-04 (первая часть) 2026-09-09.
- **Причина**: состояние `connected` знает ровно одно — «соединение установлено». Про наличие данных оно не знает ничего, и подпись утверждала больше, чем состояние способно проверить. Родня B-018, но с другой стороны: там подлинность себе назначал драйвер, здесь её дописывала подпись.
- **Решение**: подпись приведена к фактическому знанию — «Соединение установлено» / «Connection established» в четырёх каталогах (`apps/web`, `apps/cabinet` × ru/en) и в умолчаниях `ConnectionDot` (`packages/ui`). **При починке нашлось второе место того же утверждения**: `instruments.statusLive` («Котировки в реальном времени» / «Real-time quotes») выводится в `InstrumentsBrowser` ровно по `status === 'connected'` — то есть по тому же признаку и рядом с той же точкой; заменено на «Соединение с фидом установлено». Закреплено тремя тестами-растяжками (`packages/ui/.../ConnectionDot.test.tsx`, `apps/web/lib/connection-captions.test.ts`, `apps/cabinet/lib/connection-captions.test.ts`): они проверяют не равенство строке, а **отсутствие обещания данных** в подписи, привязанной к оси соединения. Мутации: возврат старой подписи в `ConnectionDot` уронил 2 теста, в каталоги витрины — 4, в каталог кабинета — 1. Изменение контракта не потребовалось: правится пользовательский текст, тип состояния не трогали.
- **Урок**: **починив ложную подпись у индикатора, ищи то же утверждение в тексте рядом с ним.** Подпись точки и строка статуса рисуются по одному признаку, но живут в разных ключах каталога — заменив первую и не тронув вторую, мы убрали бы ложное утверждение из тултипа и оставили его **видимым текстом**, то есть в единственном месте, которое пользователь читает. Признак, по которому искать: не «где написано про реальное время», а **«что ещё выводится по условию `status === 'connected'`»**. И отдельно: обещание про данные имеет право дать только состояние, которое данные видит; до появления таймера тишины транспорта (вторая часть CAB-04) такого состояния у нас нет, и это записано рядом с кодом, чтобы подпись не вернули «как было понятнее».

### B-023 · Приватный ключ подписи SSO лежит в публичном репозитории

- **Симптом**: не наблюдался — найден при задаче про генерацию ключа для разработки 2026-09-09. `docker-compose.yml` в корне монорепо, строка `SSO_PRIVATE_KEY_B64: LS0tLS1CRUdJTiBQUklWQVRFIEtFWS0tLS0t…` — это base64 от `-----BEGIN PRIVATE KEY-----`, полный RSA-ключ PKCS#8 открытым текстом. Репозиторий `github.com/MyxaCe/Sait_Platform` **публичный**.
- **Причина**: ключ добавлен коммитом `b8efc13` («SSO for the terminal…») как «dev-ключ RS256; на VPS — секрет» — то есть намерение было правильным, а исполнение положило секрет в файл, который коммитится. Компоуз контура (`deploy/vps/docker-compose.yml`) с самого начала брал значение из `.env` через `${SSO_PRIVATE_KEY_B64}`, и его `.env.example` пустой — то есть **правильный образец существовал рядом**, а корневой компоуз про него не знал. Пометка «dev-ключ» и была тем, что сняло тревогу: значение выглядело учебным, хотя это тот же материал, что и боевой.
- **Решение**: в корневом `docker-compose.yml` значение заменено на `${SSO_PRIVATE_KEY_B64:-}` — берётся из `.env` рядом с файлом (`.env` в `.gitignore`, проверено `git check-ignore`). Не задан → кабинет поднимается, `/api/sso/jwks` отдаёт `503 sso_not_configured`; это честный отказ, а не тихая подмена. Заведён `apps/cabinet/.env.example` — только имена переменных и команда генерации, ни одного значения. Dev-ключ сгенерирован в `apps/cabinet/.env.local` (покрытие `.gitignore` доказано `git check-ignore -v`, а не чтением правила). **Это не закрывает утечку**: `b8efc13` уже в `origin/main`, ключ достаётся из истории любым клоном, а force-push у нас запрещён. Закрывает её только ротация — ключ считается скомпрометированным с момента первого пуша, вопрос вынесен штабу.
- **Урок**: **«dev» — это утверждение о назначении, а не о свойствах материала.** Dev-ключ криптографически неотличим от боевого и подписывает такие же токены; отличается только то, куда его согласились поставить, а это решает следующий читающий, не автор. Отсюда правило: **приватный ключ не кладётся в коммитимый файл никогда, даже с пометкой «dev»** — граница проходит по типу материала, а не по намерению. Второй урок процедурный: гейт перед пушем у нас проверяет `git status --porcelain | grep -i env`, то есть **имена файлов в рабочем дереве**. Секрет, лежащий внутри уже закоммиченного `docker-compose.yml`, через этот фильтр проходит не задерживаясь — гейт по имени файла не ловит секрет по содержимому, и три сессии его не заметили. Проверять надо и содержимое: `-----BEGIN … PRIVATE KEY-----` и его base64-префикс `LS0tLS1CRUdJTi`.

### B-022 · `403 ACCESS_REFUSED` приходит на `exchange.declare`, а не на `queue.declare`

- **Симптом**: консюмер не поднимается при строгих правах шины. В документации и в `ЗАДАЧИ.md` отказ был записан как «403 на `queue.declare`» — то есть чинить предлагалось права на очередь.

- **Причина**: первый топологический вызов подписчика — `assertExchange` (`apps/consumer/src/subscriber.ts:40`), и только следующей строкой `assertQueue`. `exchange.declare` требует `configure` **всегда**, даже когда обменник уже существует. До объявления очереди консюмер не доходит вовсе. Тот же вызов стоит и в релее (`apps/relay/src/publisher.ts:39`).

- **Решение**: кредл `cabinet` заведён командой `deploy` (BUS-01), сквозной прогон прошёл: событие применилось, запись в `processed_events`, счёт обновлён, сбойное ушло в DLQ. Пассивное объявление обменника — задача REL-03, порядок обязателен: сначала код, потом сужение прав.

- **Урок**: **диагноз «отказ на шаге N» проверяется по порядку вызовов в коде, а не по тому, какой шаг казался главным.** Выданные по неверному диагнозу права на очередь не изменили бы ничего, а отказ остался бы прежним — и это выглядело бы как «права не помогли», уводя ещё дальше. Проверять, до какого вызова исполнение вообще доходит, прежде чем чинить тот, на который думаешь.



### B-021 · Простой консюмера без `BUS_URL` — конфигурация контура, а не поломка

- **Симптом**: консюмер на контуре ничего не делает. Легко принять за ту же аварию, что и `403` на правах шины, и «починить» одним действием.

- **Причина**: поломки нет. `createSubscriber()` (`apps/consumer/src/subscriber.ts:76-77`) при отсутствующем `BUS_URL` возвращает `NullSubscriber`, который честно пишет в лог `BUS_URL not set — idle`. Процесс держится таймером `keepAlive`, иначе Node вышел бы и restart-policy крутила бы сервис в цикле рестарта.

- **Решение**: ничего не менять. Запись существует, чтобы этот простой не смешивали с B-022: это два независимых стопора, и закрытие одного не закрывает другой.

- **Урок**: **два независимых стопора требуют двух записей, иначе закрытие одного засчитывается за оба.** Пока причины лежат в одной записи, любое улучшение выглядит как «починили», и вторая причина всплывает месяцем позже как новая. Признак, по которому их надо разводить: у них разные условия воспроизведения — здесь пустая переменная, там права брокера.



### B-020 · Невалидное сообщение подтверждалось и исчезало без следа

- **Симптом**: из трёх доставленных консюмеру сообщений одно подтверждено `ack` и потеряно, два ушли в DLQ. Замерено командой `deploy` на счётчиках брокера — в логе, в DLQ и в трекере ошибок про потерянное не было ничего.

- **Причина**: `apps/consumer/src/index.ts` начинался с `const event = parseMessage(raw); if (!event) return;`. `parseMessage` возвращал `null` в трёх РАЗНЫХ случаях — сломанный конверт, чужой тип события, наш тип со сломанным payload, — а вызывающий имел на все три один исход: тихий `return` и `ack`. Мягкий разбор был реализован как «исчезает без следа» вместо «не падает».

- **Решение**: `parseMessage` заменён на `classifyMessage`, возвращающий размеченный результат `terminal-event | foreign | malformed`. Чужой тип — счётчик и `console.debug`, пропуск остаётся правильным поведением (без него нельзя выкатывать части платформы порознь). Наш тип со сломанным payload и сломанный конверт — счётчик, `console.warn`, отправка в трекер и `throw`, по которому подписчик делает `nack` в DLQ. `event_id` сохраняется и у сломанных: без него в DLQ нечего искать. 7 тестов, 3 намеренные поломки.

- **Урок**: **мягкий разбор означает «не падает», а не «исчезает без следа».** Отдельно: **функция, возвращающая `null` по нескольким разным причинам, делает эти причины неразличимыми для вызывающего** — и он неизбежно обработает их одинаково, даже когда они требуют противоположных действий. Если причин несколько, тип возврата обязан их различать; `null` — это ответ «нет», а не ответ «почему».



### B-019 · Проверка «что будет без переменной» едва не подтвердилась на экземпляре, где переменные заданы

- **Симптом**: при перепроверке таблицы «переменная не задана → что будет» (WEB-01) семь ручек ответили не тем, что записано: `/api/health/ready` дал `database: "failed"` вместо `skipped`, `/api/revalidate` — 401 вместо 503, CSP назвал `localhost:3101` вместо `3001`. Найдено 2026-09-03 по наводке штаба «докажи, что конфигурации действительно нет».

- **Причина**: `next start` упал с `EADDRINUSE`, и запросы ушли на **другой экземпляр того же приложения** — контурный `broker-local-web-1` в Docker, где `DATABASE_URL`, `CMS_WEBHOOK_SECRET` и `PREVIEW_SECRET` заданы. Ответы выглядели штатно, потому что приложение то же самое: `/api/health` у обоих отдаёт `{"status":"ok","service":"site-web"}` — поле `service` называет ПРИЛОЖЕНИЕ, а не экземпляр. Отличить их по ответу нечем; спасла только случайность — порт оказался занят, и падение было видно. Будь порт свободен, сервер бы поднялся, а разница осталась бы незамеченной.

- **Решение**: в `/api/health` обоих приложений добавлены `instance` (host + pid + startedAt) и `config` — отпечаток конфигурации: КАКИЕ переменные заданы, но не что в них лежит, только булевы значения. Признаки экземпляра подобраны так, что экземпляр не выбирает их себе сам: `host` в контейнере это его id, `pid` разводит два процесса на одной машине. `FRAME_ANCESTORS` в отпечаток не входит сознательно — он читается на сборке, и в готовом образе поле соврало бы «не задано» о действующем значении. Dev-сервер витрины запинен на свободный порт (`next dev -p 3200`): Next без `-p` при занятом порте молча уходит на соседний. В `docs/Локальный запуск.md` — карта занятых портов и раздел «сначала докажи, что отвечает твой процесс». Таблица переменных перепроверена заново и уже методически: отсутствие `.env`/`.env.local`/`.env.development`, отсутствие переменных в оболочке, эффект каждой снят с процесса, чей `✓ Ready` наблюдался лично.
- **Урок**: **отрицательный результат про конфигурацию действителен только вместе с доказательством, какой экземпляр отвечал.** Health-ручка, называющая приложение, а не экземпляр, для этого не годится: два инстанса одного приложения с разной конфигурацией дают неотличимые ответы, и проверка «без переменной» тихо превращается в проверку «с переменной». Отдельно и прямо: **здесь сработала случайность, а не методика** — порт оказался занят, `next start` упал, и падение было видно. Был бы порт свободен, сервер бы поднялся и подмена осталась бы незамеченной. Проверка, которая проходит благодаря удаче, в следующий раз не пройдёт. Родня B-018 (мок называл себя сам) и ленивого подключения релея (контейнер `Up`, с шиной ни разу не разговаривал): во всех трёх проверяющий смотрит на признак, не привязанный к проверяемому свойству.


### B-018 · Мок-фид цен показывал зелёный индикатор «Данные в реальном времени»

- **Симптом**: без `NEXT_PUBLIC_WS_URL` бегущая строка показывала случайное блуждание (`createMockDriver`), а `ConnectionDot` рядом горел зелёным с подписью «Данные в реальном времени» / «Real-time data». Посетитель и разработчик видели обычную работающую страницу с котировками. Найдено в WEB-01 (2026-09-03) прогоном самого драйвера: `connect()` эмитил `connecting` → `connected` через 400 мс независимо от того, что фида нет.

- **Причина**: мок сознательно «полностью повторял контракт боевого socket.io-драйвера» — включая поле, которым драйвер называет себя. Тип `ConnStatus` состояния «данные не настоящие» не имел вовсе: подключённость и подлинность были склеены в один вопрос. Комментарий `apps/web/lib/mds.ts` утверждал, что «деградация видна через ConnectionDot» — по коду это было неверно.

- **Решение** (изменение контракта согласовано штабом, `_brain/КОНТРАКТЫ.md` §5а): в `ConnStatus`/`ConnectionState` добавлено состояние `simulated` — отдельное, не подвид `connected`. Подлинность решает `RealtimeService` по наличию адреса источника (`live = Boolean(NEXT_PUBLIC_WS_URL)`) и подменяет любой статус на `simulated`, если адреса нет; драйвера об этом не спрашивают, и переопределить решение он не может — включая тестовый фейк. Мок дополнительно не имеет права достигать `connected`. `ConnectionDot` — серая точка без пульсации, `TickerTape` при `simulated` выводит подпись **видимым текстом** отдельной полосой над лентой (тултипа нет на тач-устройствах, а `overflow-hidden` ленты обрезал бы наложение на узком экране). Ключи `connection.simulated` заведены в обоих приложениях. 7 новых тестов, каждый проверен на покраснение от намеренной поломки.

- **Урок**: мок, неотличимый от боевого драйвера, — не заглушка, а подделка данных; верность контракту здесь была дефектом. И шире: **признак подлинности нельзя брать из того, чью подлинность проверяешь.** Драйвер, называющий себя живым, доказывает ровно ничего — решать обязана сторона, которая знает, откуда взялся сам драйвер. То же относится к любому «статусу», который сообщает о себе проверяемый компонент.



### B-017 · Сломанная фикстура роняла страницу при полностью живой CMS
- **Симптом**: не наблюдался на контуре — найден при разборе `getCms` в задаче WEB-01 (2026-09-03) и воспроизведён тестом. Если билдер фикстуры бросает исключение или перестаёт проходить свою же Zod-схему, страница отвечает 500, хотя боевая CMS жива и к ней даже не успевают сходить.
- **Причина**: `lib/cms.ts` передавал `fallback: schema.parse(buildLocal())` **аргументом** в `cmsFetch`. Аргумент вычисляется до вызова, значит его исключение летит мимо `try/catch` внутри `cmsFetch`, который и обязан ловить всё на этом пути. Три слоя изоляции (timeout → Zod → фолбэк) были выстроены против отказа соседа и не рассматривали отказ самой страховки.
- **Решение**: фикстура строится в `getCms` в собственном `try/catch`; поломка логируется (`[getCms] fixture build failed`), в `cmsFetch` уходит `fallback: undefined`. Живая CMS → боевые данные вместо 500. Лежащая CMS + сломанная фикстура → `CmsError` наружу: данных действительно нет, и это должно быть громко. Закреплено `apps/web/lib/cms.test.ts` (8 тестов, каждый проверен на покраснение от намеренной поломки).
- **Урок**: страховка, вычисляемая жадно, находится **вне** защищаемого блока и сама становится источником аварии — ровно того класса, от которого защищает. Проверять не только «сосед упал», но и «упал наш фолбэк»: у каждого страховочного механизма спрашивать, что будет, когда сломается он сам, а не то, от чего он спасает.

### B-016 · Мигратор CMS завис навсегда: dev-push и миграции смешались в одной БД
- **Симптом**: compose-сервис `migrate` висит минутами без выхода; CMS не стартует (ждёт `service_completed_successfully`).
- **Причина**: перед контейнерной миграцией та же БД была тронута dev-пушем (`push-schema.ts` для новых sites-таблиц). `payload migrate` увидел маркер dev-режима и задал ИНТЕРАКТИВНЫЙ вопрос «данные будут потеряны, продолжить?» — в контейнере без TTY отвечать некому, процесс ждёт вечно.
- **Решение**: (1) чистая БД → миграции накатываются без вопросов; (2) правило потока: на мигрируемой БД seed запускается с `NODE_ENV=production` (db-postgres отключает push — маркер не появляется); `push-schema.ts` — ТОЛЬКО для чисто-dev БД хостового dev-сервера, никогда на БД, живущей на миграциях. Зафиксировано в README CMS.
- **Урок**: у Payload dev-push и миграции — взаимоисключающие режимы ОДНОЙ БД; смешение не падает с ошибкой, а повисает на интерактивном вопросе — worst case для автоматизации. Любой CLI-шаг в контейнере проверять на скрытую интерактивность.

### B-015 · Preview-редирект уводил на http://0.0.0.0:3000 (ERR_ADDRESS_INVALID)
- **Симптом**: кнопка Preview из админки открывает `http://0.0.0.0:3000/…`, браузер отвергает адрес (найдено пользователем 2026-07-25 сразу после фикса B-014).
- **Причина**: в standalone-контейнере Next собирает `request.url` от адреса, на котором слушает сервер (`HOSTNAME=0.0.0.0`), а не от Host браузера; `/api/preview` строил redirect от `url.origin`. На VPS за прокси тот же код редиректил бы с домена на внутренний хост — прод-баг, пойманный локально.
- **Решение**: `requestOrigin()` в `lib/preview.ts` — origin из `Host`, за прокси из `X-Forwarded-Host`/`X-Forwarded-Proto`, фолбэк на `url.origin`; применён в обеих ручках preview (вход и выход) + 3 unit-теста.
- **Урок**: в контейнере/за прокси `request.url` — это взгляд СЕРВЕРА, а не браузера; любой absolute-redirect обязан строиться от Host/X-Forwarded-*. Проверять Location-заголовки явно (`AllowAutoRedirect=false`) — автотесты с относительными fetch этого не видят.

### B-014 · Вкладка Preview в админке CMS показывала пустоту
- **Симптом**: вкладка Preview в документе Payload не работает (пусто), при этом кнопка «открыть превью в новом окне» работает (найдено пользователем 2026-07-25).
- **Причина**: вкладка Preview рендерит сайт во **iframe**, а сайт с первого дня отдаёт `X-Frame-Options: DENY` (анти-clickjacking) — браузер молча блокирует встраивание.
- **Решение**: XFO заменён на CSP `frame-ancestors 'self' <origin админки CMS>` — тот же анти-clickjacking, но с allowlist; origin для прод-сборки передаётся build-аргументом `FRAME_ANCESTORS` (headers Next фиксируются на сборке).
- **Урок**: защитные заголовки и embed-фичи конфликтуют молча (никакой ошибки, просто пустой iframe); при включении любого «встраиваемого» UX проверять всю цепочку заголовков. И наоборот: ослабляя защиту — ослаблять точечно (allowlist), а не выключать.

### B-013 · brand.socials не рендерились нигде на сайте
- **Симптом**: соцсети заполнены в CMS (и в фикстурах с этапа 0), но на сайте их не найти — ручная проверка пользователя (2026-07-24).
- **Причина**: поле контракта прошло весь путь (Zod-схема → фикстуры → CMS-глобал → ответ API), но ни один компонент сайта его не потреблял: SiteFooter не имел пропа socials.
- **Решение**: SiteFooter принимает `socials` (иконки telegram/youtube/x + текстовый фолбэк для незнакомых сетей), marketing-layout передаёт `brand.socials`.
- **Урок**: контрактное поле без потребителя в UI — мёртвое поле, и контрактные тесты его не ловят (они сверяют данные, не рендер). При добавлении ресурса в контракт сразу фиксировать, какой компонент его показывает; финальная сверка «поле → место на странице» — обязательный шаг этапа.

### B-012 · Откат версии в CMS не долетал до сайта
- **Симптом**: восстановление предыдущей версии в админке (Versions → Restore) выглядит успешным, published-API CMS сразу отдаёт откаченный контент, но сайт продолжает показывать старое — «откат не работает» (найдено пользователем 2026-07-24).
- **Причина**: у Payload при restore в хук `afterChange` документ приходит со `_status: 'draft'` (даже когда восстанавливается published-версия и published-контент реально меняется). Наш `notifyAfterChange` фильтрует черновики → вебхук инвалидации молча пропускался, ISR-кеш сайта жил до страховочного revalidate (час).
- **Решение**: в `notifyAfterChange` restore распознаётся по URL запроса (`…/versions/:id`) и вебхук шлётся всегда, независимо от `_status`.
- **Урок**: родственник B-011 — на пути «событие о состоянии → инвалидация» любой молчаливый фильтр обязан быть доказан для КАЖДОЙ операции источника (create/update/publish/restore), а не только для основной; restore — та самая операция, ради которой версии и существуют, и именно её никто не проверил живьём.

### B-011 · Cooldown вебхука терял инвалидацию вместо откладывания
- **Симптом**: живая проверка петли «правка в CMS → вебхук → сайт»: первая публикация видна на сайте за 0,9 с, откат следом — не виден вовсе (до часа, пока не сработает страховочный ISR). В логах: `applied=[] throttled=[cms:faq]`.
- **Причина**: анти-шторм cooldown (2 с на тег) **отбрасывал** событие, попавшее в окно, а не откладывал: две публикации подряд по одному ресурсу — вторая (актуальная!) терялась.
- **Решение**: `claimDeferredInvalidate()/completeDeferredInvalidate()` в `lib/revalidate.ts` — опоздавший запрос вебхука **сам дожидается конца окна внутри обработчика** (≤2 с) и инвалидирует перед ответом; параллельные события того же тега коалесцируются. Ответ вебхука: `throttled` → `deferred` (обновлён и OpenAPI-артефакт). Проверено живой петлёй: правка — 0,2 с, откат внутри cooldown — 3,1 с.
- **Урок** (двойной): 1) rate-limit на *событиях о состоянии* обязан быть «debounce с гарантией последнего», а не «drop» — терять допустимо промежуточные срабатывания, но не финальное; 2) первая версия фикса через `setTimeout` не работала: `revalidateTag()` живёт только в контексте запроса, после ответа это тихий no-op без единой ошибки в логах. Найден только живой E2E-петлёй с реальной CMS — unit-тесты cooldown проходили.

### B-010 · Health-эндпоинты замораживались на билде
- **Симптом**: `/api/health/ready` отдавал `db=skipped` при заданном DATABASE_URL; `time` в `/api/health` не менялся. Найден собственным синтетическим монитором при первом же запуске.
- **Причина**: GET route-handlers без динамических API Next 14 пререндерит статически — ответ зафиксировался в момент сборки (когда env ещё не было).
- **Решение**: `export const dynamic = 'force-dynamic'` в обоих health-роутах.
- **Урок**: любой GET-хендлер, чей ответ зависит от времени/env/состояния, обязан объявлять `force-dynamic`; синтетика окупилась до прода.

### B-009 · Cooldown вебхука блокировал первую инвалидацию тега
- **Симптом**: unit-тест `shouldInvalidate` упал — первый же вызов для тега возвращал false.
- **Причина**: «никогда не инвалидировался» кодировался как `last = 0`, и при малых значениях `now` условие `now - last < cooldown` считало тег «недавним».
- **Решение**: явная проверка `map.has(tag)` (undefined ≠ 0).
- **Урок**: сентинельные значения (0/пустая строка) в временной логике — источник edge-багов; тест с фейковыми таймстампами это ловит, прод с Date.now — маскирует.

### B-008 · CI падал на pnpm/action-setup
- **Симптом**: первый прогон GitHub Actions упал на шаге `pnpm/action-setup@v4`, все последующие шаги skipped.
- **Причина**: версия pnpm была задана дважды — входом `version: 9` в workflow и полем `packageManager` в package.json; экшен считает это конфликтом.
- **Решение**: убрали `version` из workflow — экшен читает версию из `packageManager` (fix `9478c37`).
- **Урок**: единственный источник версии тулчейна — `packageManager`; в CI её не дублировать.

### B-007 · DYNAMIC_SERVER_USAGE при рендере 404 (production)
- **Симптом**: неизвестный инструмент/статья → 500 c digest `DYNAMIC_SERVER_USAGE` вместо 404 (только в production-сборке).
- **Причина**: в динамических страницах `notFound()` вызывался ДО `setRequestLocale(locale)` — рендер 404-границы уходил в динамический режим без установленной локали.
- **Решение**: `setRequestLocale` — первой строкой каждой динамической страницы, до любых проверок.
- **Урок**: у next-intl жёсткий порядок инициализации; e2e на 404 обязателен — dev-режим этот баг маскирует.

### B-006 · 500 вместо 404 под сегментом [locale]
- **Симптом**: `notFound()` в production → 500.
- **Причина**: при route-сегменте `[locale]` Next не может отрисовать глобальный not-found — нужен свой `app/[locale]/not-found.tsx`.
- **Решение**: добавлена двуязычная 404-страница.
- **Урок**: любые «серые» состояния (404, offline, error) проверять production-сборкой, не dev.

### B-005 · Автодетект языка уводил пользователей с RU-версии
- **Симптом**: e2e упали — `/` отдавал английский hero; то же ждало реальных пользователей с англоязычной ОС/браузером.
- **Причина**: middleware next-intl по умолчанию редиректит по `Accept-Language`.
- **Решение**: `localeDetection: false` — язык только URL + переключатель ([[Решения (ADR)#ADR-008]]).
- **Урок**: e2e в headless-браузере — отличный «иностранный пользователь» бесплатно.

### B-004 · Production-сборка ломала работающий dev-сервер
- **Симптом**: после `pnpm build` dev-сервер отдаёт 500 `Cannot find module './vendor-chunks/...'`.
- **Причина**: build и dev делят каталог `.next` — сборка перезаписывает кеш живого dev.
- **Решение/процесс**: не запускать build при работающем dev; после build — перезапуск dev с удалением `.next`. Повторился при проверке CRM-задания (на :3000 висел старый dev — прод-сервер не стартовал, порт занят): всегда проверять, кто слушает порт.
- **Урок**: в CI/Docker неактуально (изолированные каталоги), локально — только последовательно.

### B-003 · Строгие локаторы Playwright: «1:500» нашлось дважды
- **Симптом**: e2e падал strict mode violation — текст «1:500» есть и в абзаце, и в ячейке.
- **Решение**: `getByText('1:500', { exact: true })`.
- **Урок**: для коротких значений всегда exact/role-локаторы.

### B-002 · Типы: `actual: null` vs `string | undefined` (calendar-data)
- **Симптом**: tsc падал на шаблонах календаря.
- **Решение**: тип поля `actual?: string | null`.
- **Урок**: strict-режим ловит контрактные несоответствия — не ослаблять.

### B-001 · `process.env` в пакете без @types/node
- **Симптом**: typecheck `packages/realtime` падал на `process.env.NEXT_PUBLIC_WS_URL`.
- **Решение**: `@types/node` в devDependencies пакета.
- **Урок**: каждый пакет объявляет свои типы окружения сам.
