# Технический долг

Осознанно отложенное. Каждая запись: что, почему отложено, когда возвращаться, цена промедления.

## TD-015 · Срок годности allow-list выбираем мы, а должен приходить от источника
- **Что**: граница доступа к инструментам (ADR-029) живёт в статической сборке витрины и обновляется ISR с `revalidate: 300` плюс вебхуком карточки сайта. Пока окно не истекло, страница показывает **прежний** список — то есть ограниченный по времени last-good, причём срок годности (5 минут) выбран потребителем. КОНТРАКТЫ.md §4б разрешает такой кеш только со сроком, приходящим **от источника**: «порог свежести задаёт MDS, а не потребитель».
- **Почему отложено**: вариантов два, и оба за пределами задачи. Либо `/v1/cms/sites/{slug}` начинает отдавать свой TTL — это изменение контракта CMS→сайт, решает штаб. Либо страницы инструментов становятся динамическими — это отмена части ADR-009 (ISR как способ доставки контента) с понятной ценой в скорости и SEO. Сделать это внутри Р-025 в одиночку значило бы поменять контракт без штаба.
- **Когда возвращаться**: вместе с Р-026 (валидация содержимого списка в CMS) — обе задачи про один и тот же эндпоинт, и TTL логично добавить тем же заходом.
- **Цена промедления**: инструмент, запрещённый юрисдикцией, остаётся видимым и кликабельным до 5 минут после правки в CMS, если вебхук не дошёл. Вебхук — единственное, что сегодня делает окно нулевым, и его доставка ничем не гарантирована.

## TD-016 · Браузер инструментов витрины не покрыт e2e в CI
- **Что**: после ADR-029 страница «Инструменты» при незаданном `CMS_API_URL` показывает объяснение вместо списка — а в CI сервер поднимается именно без CMS. Сценарии с НЕПУСТЫМ списком (поиск, фильтр по категории, живая котировка на деталке) переведены под гейт `CMS_E2E=1` и в CI не гоняются. Покрытие единицы (`lib/tenant.test.ts`) покрытием пути не является.
- **Почему отложено**: закрывается стабом CMS в CI, но его нельзя просто включить глобально: `isolation.spec.ts` проверяет чеклист §9.3 «сайт работает без ЕДИНОГО соседа», и поднятая CMS отменяет его премиссу. Нужны два профиля Playwright с разными `webServer` — это перестройка e2e-обвязки, отдельная задача.
- **Когда возвращаться**: при следующей правке чего-либо в `features/instruments/` — иначе регресс там обнаружится только руками.
- **Цена промедления**: фильтры и поиск браузера инструментов не проверяются ничем автоматическим; та же дыра у `mds-live.spec.ts`, который теперь требует ещё и непустой allow-list.

## TD-014 · Кастомные (синтетические) инструменты — «USD/BTC x10» и т.п.
- **Что**: возможность собирать производные инструменты из базовых фидов MDS — инверсия (USD/BTC = 1 / BTCUSD), множитель/плечо («x10»), корзины/спреды. Считаются в MDS в реальном времени, во вселенной появляются с провайдером `custom`/`synthetic`, сайт выбирает их в allow-list как обычные.
- **Почему отложено**: решение пользователя 2026-07-27 — «пока не нужно». Плюс есть неоднозначности: семантика «x10» (простое масштабирование от точки отсчёта против настоящего leveraged-токена с ежедневной ребалансировкой и decay), и место определения (формула в MDS платформенно против конструктора в CMS — последнее тянет за собой CMS→MDS зависимость, которую ADR-027 разрывал).
- **Когда возвращаться**: когда бизнес попросит нестандартные инструменты. UI-фильтр по провайдеру в MdsAllowListField уже готов принять группу `custom`.

## TD-010 · ContentAutoRefresh опрашивает страницу целиком
- **Что**: автообновление открытой страницы (2026-07-24) раз в 10 с делает GET текущего URL и парсит метку `rendered-at` из HTML (~100 КБ на опрос из ISR-кеша). Легче было бы HEAD/микро-эндпоинт «версия контента по пути», но серверу неоткуда знать rendered-at страницы без её рендера.
- **Почему отложено**: трафик копеечный (кеш, gzip), реализация надёжная и без нового API.
- **Когда возвращаться**: при заметном трафике от опросов на проде либо вместе с миграцией инвалидации на шину (тогда версии тегов можно раздавать из своего стора и слать push вместо poll).

## TD-011 · Схема БД CMS: dev-push вместо миграций Payload — ✅ ЗАКРЫТ 2026-07-25
Закрыт в тот же день: initial-миграция в `src/migrations` Broker_CMS, compose-порядок db → migrate → cms, репетиция на чистой БД. Dev на хосте остаётся на push (это норма), прод — только миграции.

## TD-012 · Дубли rate-limit/honeypot-хелперов в web и cabinet
- **Что**: `lib/rate-limit.ts` скопирован из apps/web в apps/cabinet (кабинет, ADR-022); honeypot-паттерн тоже повторён в Zod-схемах.
- **Почему отложено**: хелперы по ~20 строк, выделение в `packages/utils` в момент создания кабинета удлиняло критический путь.
- **Когда возвращаться**: при третьем потребителе (терминал) или переезде rate-limit на Redis (TD-003) — тогда одна реализация обязательна.
- **Цена промедления**: поведение лимитов может разъехаться между приложениями незаметно.

## TD-013 · Кабинет: e2e не гоняется в CI
- **Что**: `apps/web/e2e/cabinet.spec.ts` (полный цикл регистрация→дашборд→выход→вход→дубль email) скипается без env `CABINET_URL` — в CI кабинет и Postgres со схемой 002 не поднимаются.
- **Когда возвращаться**: следующее касание CI — поднять postgres-сервис + `next start` кабинета и включить спеку.
- **Цена промедления**: регрессии auth-флоу ловятся только локальным прогоном.

## TD-001 · Конструктор страниц (page builder) ⭐ решение пользователя, 2026-07-23
- **Что**: страницы как массив JSON-секций из `GET /api/cms/pages?slug=`, реестр `SECTION_REGISTRY` (type → Zod-схема + компонент), неизвестный тип = skip+лог. Для маркетинговых лендингов (главная, промо, about, partners).
- **Почему отложено**: самая дорогая и рискованная часть CRM-интеграции; типизированные эндпоинты дают ~80% ценности. [[Решения (ADR)#ADR-010]].
- **Когда возвращаться**: после этапов 0–3, когда маркетингу понадобятся лендинги без деплоя.
- **Заготовки уже есть**: секции-компоненты главной изолированы; контракт `pages` заложить в OpenAPI на этапе 0 (пустым), чтобы CRM могла проектировать редактор заранее.

## TD-002 · Общий ISR-кеш при масштабировании
Один VPS-инстанс — файлового кеша достаточно. При втором инстансе/контейнере обязателен custom `cacheHandler` (Redis) — иначе `revalidateTag` инвалидирует кеш только одного инстанса (разный контент у пользователей). Триггер: решение о horizontal scaling.

## TD-003 · Rate-limit форм на Redis
`lib/rate-limit.ts` — in-memory, корректен для одного инстанса. Триггер тот же, что TD-002.

## TD-004 · BroadcastChannel/WS-инвалидация React Query
Из CRM-задания; для маркетингового сайта бесполезна (контент и так через ISR). Понадобится личному кабинету — реализовать там.

## TD-005 · Вычитка EN-контента носителем
