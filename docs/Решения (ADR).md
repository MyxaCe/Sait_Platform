## ADR-001 · Turborepo + pnpm
Сайт, кабинет, терминал и CRM-админка делят ui/realtime/utils/контракты. Nx избыточен на старте. Последствие: ломающие изменения пакетов ловятся на CI всех потребителей.

## ADR-002 · App Router, максимум статики
Каждая страница — SSG/ISR (сейчас 153 SSG-страницы), клиент получает готовый HTML. Динамика гидрируется поверх. Это фундамент SEO и Core Web Vitals — любое решение, ломающее статичность, отклоняется (см. ADR-009).

## ADR-003 · Токены только через CSS-переменные
RGB-каналы ради модификаторов прозрачности (`bg-accent/10`). Смена темы/бренда — атрибут на `<html>`, без пересборки. Готовый фундамент White Label: бренд из CRM = одна `<style>` со значениями переменных.

## ADR-004 · Realtime за интерфейсом FeedDriver
Мок и боевой socket.io-драйвер неразличимы для стора и UI; переход на реальный фид = env-переменная. Подписки по счётчику ссылок. `connect(customDriver?)` — тестируемость.

## ADR-005 · Кабинет отдельным приложением
Module Federation отвергнут: изоляция сбоев, независимые деплои, кабинету не нужен SEO. Единообразие — через общие пакеты и SSO (JWT в памяти + refresh httpOnly cookie на `.domain`).

## ADR-006 · Без страницы /platforms
Торговая платформа существует как отдельный модуль (решение пользователя). Ссылки убраны из header/footer; вернутся при интеграции модуля.

## ADR-007 / ADR-008 · i18n
Все маршруты под `[locale]`; `as-needed` (ru чистые URL — SEO-совместимость со стартовой версией). Автодетект по Accept-Language **выключен**: уводил англоязычные браузеры (и headless-тесты) на /en с чистого URL — язык предсказуем: URL + переключатель. Найдено e2e-тестами — [[Журнал багов#B-005]].

## ADR-009 · Серверный ISR вместо клиентского React Query для контента ⭐
Исходное задание требовало «все страницы через хуки React Query» — это противоречило его же пунктам 1–2 (статика с CDN, 0 запросов с клиента) и уничтожило бы SEO/CWV. Принято: контент — серверный fetch в RSC с `next:{tags,revalidate}` + `revalidateTag()` по вебхуку (`res.revalidate` — Pages Router API, не наш случай). React Query — только клиентский интерактив (пагинация, live-статусы, формы) и будущий кабинет. Согласовано с пользователем.

## ADR-010 · Конструктор страниц → тех. долг
Самая дорогая и рискованная часть CRM-задания. Отложен решением пользователя; типизированные эндпоинты дают 80% ценности без него. Детали: [[Технический долг#TD-001]].

## ADR-011 · Полный перевод и ключи валидации
Контент — per-locale массивы в data-файлах (`getX(locale)`), слаги общие (`*_SLUGS` для generateStaticParams/sitemap). Zod-сообщения — ключи namespace `validation`: одна схема на клиенте и сервере, перевод при отображении (`t.has(key) ? t(key) : key`), серверные fieldErrors языконезависимы.

## ADR-012 · UI-кит без текстов
`PricingTable`, `TickerTape`, `ConnectionDot` принимают labels-пропсы (RU-дефолты для обратной совместимости). Дизайн-система остаётся независимой от next-intl — переиспользуема в кабинете/админке.

## ADR-023 · Терминал — White Label-поставщик; интеграция контрактами, не кодом (2026-07-25)
**Контекст**: терминал — наша, но независимая система (после их пивота — автономная торговая страница). Целевая модель пользователя: 1 терминал ↔ N страновых сайтов, настройки каждого сайта в нашей CMS. Монорепо-вариант отклонён пользователем (и это верно: у поставщика на N потребителей своя причина жить отдельно — ADR-016).
**Решения** (по ответам команды терминала, детали и статусы — [[Интеграция с терминалом]]):
1. **Поставка — iframe** из кабинета; `frame-ancestors` конфигурируемым списком доменов сайтов (урок B-014). JS-виджет не делаем.
2. **Один мульти-тенантный инстанс**; тенант для авторизованных — в токене, для публичного/дологинного — `?site=`/поддомен. Конфиг тенанта = наш контракт `/v1/cms/*?site=` → CMS становится мульти-тенантной (коллекция sites) — следующий крупный этап CMS.
3. **Темизация в рантайме**: контракт = CSS-токены (артефакт) + `GET /v1/cms/brand`; адаптер пишет команда терминала. Одна сборка — все бренды (токены RGB-каналами были заложены под это с первого дня).
4. **SSO**: сессии платформы остаются opaque+revocable (ADR-022); терминалу выдаётся короткоживущий one-shot JWT (sub, tenant, exp≤60с, jti) через postMessage; выпуск и JWKS — новый **Auth-сервис** (триггер ADR-017 сработал: один терминал × много сайтов).
5. **Демо-счёт — ❌ их предложению «кабинет читает /account»**: синхронных вызовов соседей на пути клиента не будет (золотое правило, ADR-018). Терминал владеет торговым состоянием, но публикует события в `platform.events` (конверт v1, свой outbox); кабинет и CRM строят проекции — та же модель, что лиды.
6. **Условия старта**: `/v1`-префикс их контрактных ручек, схемы в platform-contracts, символ-маппинг (наши канонические `BTCUSD` ↔ их `BTC-USDT`) в контракте инструментов.
**Наша критическая цепочка**: theming-пакет → JWT/JWKS-спека (с Auth-сервисом) → CMS sites-контракт. Мы блокируем их работы — отдаём первыми.

## ADR-022 · Личный кабинет: apps/cabinet + собственный auth (2026-07-25)
**Контекст**: этап «логин, регистрация, личный кабинет» (решение пользователя). CRM ещё не подключена к шине — первый кабинет работает на наших данных (статус заявки, профиль, демо-счёт), реальные счета придут с интеграцией.
**Решение 1 — отдельное приложение `apps/cabinet` в монорепо сайта** (подтверждено пользователем; вариант «маршруты внутри сайта» отклонён). Кабинет — приватное приложение с противоположным сайту профилем: всё динамическое, сессии, без ISR/SEO; у сайта — SSG и перф-бюджеты. Это НЕ отдельная система (в отличие от CMS, ADR-021): общая БД платформы, общий деплой-конвейер, общие пакеты ui/utils/api-client — потому монорепо, а не отдельный репозиторий; ровно случай «отдельная деплой-единица, но фронтенд» из ADR-017. Порт 3002, свой контейнер.
**Решение 2 — свой auth внутри кабинета, БЕЗ выделенного Auth-сервиса на MVP** (ADR-016: сервис — только при собственной причине жить отдельно; потребитель auth сегодня один). Реализация: users/sessions в Postgres платформы (та же БД `broker_site` — кабинет в одном failure domain с сайтом по ADR-018), пароли bcrypt, **opaque session-токен в httpOnly-куке** (в БД — sha256-хеш токена: ревокация сессий из UI, никакого JWT — нечего инвалидировать). Выделение Auth/SSO-сервиса — при старте терминала (триггер из ADR-017), таблицы и семантика переезжают как есть.
**Решение 3 — регистрация в кабинете = открытие счёта**: в ОДНОЙ транзакции user + lead(kind account-opening) + outbox `lead.submitted` (тот же конверт v1 — для CRM ничего не меняется) + welcome-уведомление + демо-счёт $10 000. Сайтовые кнопки «Войти/Открыть счёт» ведут в кабинет (`NEXT_PUBLIC_CABINET_URL`); старая форма-заявка сайта остаётся рабочей (второй вход воронки), решение о её судьбе — после интеграции с CRM.
**MVP-объём** (подтверждён пользователем): auth + дашборд (статус заявки, демо-баланс, живые котировки через `FeedDriver`) + профиль + безопасность (смена пароля, список сессий с ревокацией) + документы (KYC-заглушка: локальная загрузка со статусами, при интеграции переезжает на процесс CRM) + уведомления (welcome-события сейчас, консюмер шины — фаза 2).
**Схема БД**: `db/init/002_cabinet.sql` (users, sessions, demo_accounts, documents, notifications; FK на users, все — наша сторона платформы).

## ADR-021 · Собственный CMS-сервис на Payload CMS 3 (2026-07-24)
**Контекст**: CMS — отдельная независимая система (решение пользователя); строим её сами.
**Решение (уточнено по возражению пользователя)**: Payload CMS v3 в **ОТДЕЛЬНОМ репозитории** (не монорепо сайта) — граница системы должна быть границей репозитория: свой CI/деплой/доступы (редакция контента без кода сайта), деплои не сцеплены. Монорепо-вариант отклонён: соблазн общего Zod-импорта размывает границу; ADR-020 «шов = границы пакетов» — про слои ВНУТРИ системы, CMS — другая система.
**Контракт без общего кода**: канон — JSON Schema + фикстуры в `platform-contracts` (расширение ADR-019); сайт валидирует Zod'ом, CMS — теми же JSON Schema через ajv на выходе ручек; контрактные тесты обеих сторон на общих фикстурах (28 эталонных фикстур экспортированы: `packages/api-client/artifacts/fixtures/`, скрипт `scripts/export-cms-fixtures.mjs`).
Отдельная БД `broker_cms` — свой failure domain по данным.
**Почему Payload, а не своё/Strapi/Directus**: из коробки закрывает ровно те требования чек-листа спецификации, которые иначе стоят месяцы: админ-UI; **drafts + versions с откатом публикации**; **локализация per-locale полей с фолбэком на ru**; access control; **медиа через sharp — width/height/alt автоматически** (риск R-05); hooks `afterChange` для вебхуков; Local API. TypeScript-first — коллекции типизируются из тех же представлений, что наш Zod-контракт. Strapi — versioning слабее, тяжелее; Directus — чужой стек админки; полностью своё — изобретение админки.
**Контракт-first**: внутри apps/cms — route handlers `/v1/cms/*`, читающие Payload Local API и отдающие ответы, провалидированные НАШИМИ Zod-схемами из `packages/api-client` (двойная гарантия). Сайту адаптер не нужен: `CMS_API_URL` → cms-сервис. `X-API-Key` middleware; `draft=true` через Payload drafts.
**Вебхуки**: `afterChange` → подписанный POST в `/api/revalidate` сайта с ретраями (MVP); эволюция — событие `cms.content.published` в шину (как согласовано с платформой).
**Сидинг**: наши per-locale фикстуры (бывшие data-файлы) — готовые данные для seed-скрипта; день одного контента экономится полностью.
**MVP-объём**: коллекции brand/navigation/contacts/partners (globals) + instruments/accounts/faq/promotions/academy/streams/articles/careers/legal/system-status; контракт-ручки; вебхук; seed; compose-сервис `cms`.

## ADR-020 · Слои и два контракта (обсуждение 2026-07-24)
Принята модель «три слоя по скорости изменения»: **логика** (packages: realtime, api-client, LeadStore — меняется редко) → **каркас** (apps/web компоненты/страницы — часто) → **контент** (CMS — постоянно, без деплоя). Два контракта на швах:
1. **CMS → каркас**: версионированный контент. Уже реализовано ISR-архитектурой (снапшот = закреплённая версия, публикация = вебхук, Zod+last-good = защита от сломанной редактуры). Дополнение: в контракт CMS добавлена рекомендация `contentVersion`/`publishedAt` в ответах + та же версия в meta HTML — точный ответ на «какую версию видит пользователь», откат = перепубликация.
2. **Каркас ↔ логика**: стабильный узкий интерфейс. У нас это ГРАНИЦЫ ПАКЕТОВ (FeedDriver, LeadStore, CMS_RESPONSE_SCHEMAS), а не сетевой API — превращать в HTTP внутри одной системы запрещено (то самое переусложнение). Доказательство работоспособности шва: FeedDriver не менялся с первого дня через все перестройки UI; LeadStore пережил смену CRM-прокси→outbox без правки форм.
Границы независимого деплоя остаются прежними (ADR-005/017/018): контент (без деплоя), кабинет/терминал (отдельные приложения, фаза 2), сервисы. Наружу брокер — один failure domain с одним outbox. Дальше трёх слоёв не дробить.

## ADR-019 · Контракт событий: итоги ревью команды CRM (2026-07-24)
Команда CRM отревьюила нашу реализацию: блокеров нет (outbox/релей/изоляция — «на уровне прода»).
1. **Наш event-envelope принят платформенным стандартом** (у CRM конверт был семантически тот же, но с другими именами полей и без `version`); CRM пишет тонкий адаптер к своей внутренней шине, наш релей не меняется.
2. **Контракт-репозиторий `platform-contracts/`** (черновик у CRM): event-envelope.v1, lead.submitted.v1 (снят 1:1 с нашего Zod), формат шины, PII-политика; наши события уже прогнаны их jsonschema — валидны. **Наша позиция по source of truth**: в platform-contracts живут JSON Schema (нейтральная единая правда), наш Zod — имплементация на нашей стороне; контрактный тест в нашем CI валидирует эталонные фикстуры из контракт-репо нашими схемами (расхождение = красный билд).
3. **Отдельная шина `platform.events` — ПОДТВЕРЖДАЕМ** (их вопрос до созвона). Аргументы: изоляция прав и failure domain (сайту не нужны права на внутреннюю mica.events; у интеграционного контура свой vhost/учётки/лимиты); контроль PII-скоупа (в lead.submitted есть PII — доступ узкий); свобода эволюции внутренней шины CRM против версионируемого платформенного контура; blast radius (шторм внутренних событий CRM не задевает платформу).
4. Подтверждено CRM: объём Приложения А (cms-сервис отдельный, консюмер lead.submitted, сервисные ключи, width/height/alt), инвалидация этап 1 = HTTP-вебхук → потом шина, обратный поток = фаза кабинета.
Повестка созвона (финал): отдельная шина ✓ (позиции совпали), финал event-envelope.v1, свод PII-политики, хостинг контракт-репо (наше предложение — отдельный git-репозиторий с доступом обеих команд).

## ADR-018 · Платформенная модель по брифу CRM (broker-site-integration-brief.md, 2026-07-24)
**Принимаем модель платформы целиком** — она на ~90% совпадает с нашими ADR-014…017 (свой auth = ADR-017; sync-с-фолбэком = cmsFetch; котировки вне шины = Market Data; скраббинг = ADR-014). **Признанное нарушение у нас**: лид-флоу был спроектирован синхронным прокси BFF→CRM (409 emailExists от CRM) — это ломает золотое правило «никаких синхронных вызовов соседей на пути клиента». Реальный вызов CRM подключён не был (мок), переделываем до интеграции.
**Решения**: 1) сайт получает **свою Postgres** (Docker на VPS): лиды пишутся локально, клиент получает 201 сразу; 2) **transactional outbox** в той же транзакции + процесс-релей → шина платформы (topic-exchange, `lead.submitted` v1, envelope из общего контракт-репо, at-least-once → идемпотентность по event_id); 3) дубликаты email — по НАШЕЙ БД (мы source of truth клиентов брокера, §10.1 брифа принят по умолчанию); 4) синхронные `/v1/leads/*` в CRM **сняты** из интеграционной спецификации — CRM строит проекцию лида консюмером событий; доработка email в CreateClientBody перестаёт быть API-вопросом; 5) фазировка: сейчас outbox на лидах (сайт маркетинговый), полный контур `customer.registered/verified/kyc.*` — с фазой кабинета; 6) контент: этап 1 остаётся на HTTP-вебхуке `/api/revalidate`, миграция на потребление `cms.content.published` из шины — когда релей заработает (вопрос созвона §10).
**Следствие для ADR-017**: у сайта появляются БД и релей-воркер — внутри его failure domain, НЕ отдельные сервисы.

## ADR-017 · Сервисные границы нашей стороны
Тот же принцип, что ADR-016, применённый к себе: сервис — только то, у чего собственная причина жить отдельно (нагрузка, жизненный цикл, технология, команда).
**Настоящие сервисы (по триггерам):** 1) **Market Data Service** — WS-fan-out котировок, тысячи постоянных соединений, свой ритм релизов; сайт готов через `FeedDriver` (смена `NEXT_PUBLIC_WS_URL`); триггер — подключение реального фида. 2) **Auth/SSO** — выпуск JWT/ротация refresh для сайта+кабинета+терминала, изолированный периметр безопасности; триггер — старт кабинета. 3) `apps/cabinet`, `apps/terminal` — отдельные деплой-единицы, но фронтенды, не сервисы.
**Остаются слоями внутри Next.js:** BFF-прокси лидов, приёмник вебхуков, ACL-адаптер `/api/cms/*` (stateless, тонкие, меняются вместе со страницами; отдельный content-service = третье место протухания кеша без выгоды). Триггер пересмотра BFF: дублирование прокси-логики в кабинете/терминале → общий шлюз.
**Инфраструктура, не сервисы:** Redis (общий ISR-кеш TD-002 + rate-limit TD-003 + pub/sub WS; триггер — второй инстанс), synthetic-monitor (cron-скрипт, этап 3 CRM).
**Целевая гранулярность экосистемы:** 3 фронтенда + 2 наших сервиса + CRM (с новым cms-доменом) + Redis/GlitchTip ≈ 5–6 деплой-единиц. Больше — расплата операционной сложностью без выгоды.

## ADR-016 · Развязка сайт↔CRM без перестройки CRM на микросервисы
**Контекст**: внутри CRM модули плотно связаны; возник вопрос — предложить ли команде CRM полную переделку на микросервисы (discovery + RabbitMQ + Redis-очереди) как условие «держать связь на расстоянии».
**Решение**: НЕ требуем и не рекомендуем big-bang. Дистанция между сайтом и CRM обеспечивается **границей интеграции**, и она уже спроектирована: единый gateway (у CRM есть), версионированный контракт + ACL-адаптер (ADR-015), асинхронные вебхуки, никаких общих БД и кода (только нейтральные артефакты контракта). Внутренняя связность CRM через эту границу протечь не может.
**Почему не big-bang**: (1) месяцы риска без пользовательской ценности на работающей системе из ~12 сервисов; (2) неправильная последовательность — у команды пока нет наблюдаемости (26 молчаливых деградаций), а микросервисы+очереди умножают операционную поверхность (HA брокера, DLQ, мониторинг очередей); (3) discovery на одном VPS бессмыслен — DNS-имена docker-compose достаточны, discovery окупается только с динамической оркестрацией; (4) «RabbitMQ везде» без контрактов и версионирования событий = распределённый монолит с eventual-consistency-багами.
**Эволюционный путь (предложение команде CRM, в их темпе)**: 1) наблюдаемость — уже в плане (GlitchTip, 26 точек); 2) новый **cms-домен строить сразу отдельным сервисом со своей БД** за тем же гейтвеем — greenfield без связей с clients/employees, естественная первая «правильная» граница; 3) пилот событийной модели — `content.published` через **outbox-паттерн** + очередь + воркер-доставщик вебхуков (первый реальный consumer — сайт); если приживётся — расширять на внутренние домены по одному (strangler, не rewrite); 4) enforce границ существующих модулей: контракт на каждый сервис, запрет cross-domain доступа к чужим таблицам; 5) дальнейшая нарезка — по ДАННЫМ GlitchTip (каскадные инциденты, deploy lockstep), а не по архитектурной моде.

## ADR-015 · CRM — внешний продукт, интеграция через anti-corruption layer
CRM уже написана (Python FastAPI + gRPC, фронтенды React/Vite) другой командой. Сайт зависит ТОЛЬКО от собственного контракта (`packages/api-client`); маппинг реальных маршрутов CRM → контракт живёт в адаптере на стороне сайта (`app/api/cms/*` — те же файлы, что mock-CRM). Изменения в CRM API затрагивают адаптер, не страницы. Наш deliverable для команды CRM — [[Интеграционная спецификация CRM]]. gRPC — внутреннее дело CRM, сайту нужен REST JSON.

## ADR-014 · Общая наблюдаемость с CRM (GlitchTip) — согласовано 2026-07-23
- **Один общий инстанс на VPS CRM** (15 ГБ RAM, проверено ими). Ответственность зафиксирована: **бэкапы и обновления — команда CRM**, в их существующей процедуре бэкапа прода. Проекты: `site-web` (@sentry/nextjs), `site-bff`, `crm-backend` (sentry-sdk Python), `crm-frontend` (@sentry/react) — коллектор общий, различаются только SDK. Сквозной `X-Request-Id` у CRM уже реализован middleware'ом (принять/сгенерировать → в логи → вернуть в ответе) — сшивка инцидентов работает сразу.
- **Скраббинг PII — блокер первого события**, на уровне SDK (`before_send`/`beforeSend`). Политика (усилена предложениями CRM):
  - формат общего списка — **нейтральный JSON** в контракт-репозитории (`scrubbing-policy.v1.json`) + тонкие адаптеры per-SDK (TS и Python) — не TS-пакет, Python его не импортирует;
  - тела запросов — **allowlist, не denylist**: прикрепляются только явно разрешённые поля (regex по ФИО не работает — новая форма = утечка постфактум);
  - остальное как было: `sendDefaultPii: false`; headers `Authorization, Cookie, X-API-Key` — удалять; тела `/leads/*`, `/auth/*` — никогда; query `token|key|signature|email|phone` — маскировать; regex-вычистка email/phone/PAN/IBAN как второй эшелон поверх allowlist; user-контекст `{id: sha256-хэш}`.
- **Retention 30 дней**, `GLITCHTIP_MAX_EVENT_LIFE_DAYS=30`, только errors (`tracesSampleRate: 0`). Диск CRM занят на 72% (108/158 ГБ) → **чистка диска ДО установки** и алерт на **78%**, заведённый ДО первого события; пересмотр retention по факту через месяц.
- Первая очередь внедрения на стороне CRM: **26 мест молчаливой деградации в 12 сервисах** + шлюз (замена подавления на отправку события). Их сроки: ~2–3 дня работ, старт после определения сроков интеграции.

## ADR-013 · Стек CRM-интеграции
- Статьи: **Markdown (CommonMark), raw HTML запрещён**; рендер remark + rehype-sanitize. HTML = XSS-риск; структурные блоки = дорогой редактор (опция на будущее).
- Медиа: S3-совместимое хранилище (MinIO в Docker на VPS или Cloudflare R2) + CDN-домен; контракт `{url, width, height, alt, mimeType}`, width/height обязательны (анти-CLS); рендер через next/image.
- Error tracking: **GlitchTip self-hosted** (Sentry-совместимый SDK, лёгкий, данные на нашем VPS); миграция на Sentry SaaS при желании = смена DSN.
